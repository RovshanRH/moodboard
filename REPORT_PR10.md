# Отчёт по практической работе № 10

## 1. Тема и цель работы

Тема работы — «Административная панель Django и работа с данными через
ORM».

Цель работы — освоить настройку Django Admin, расширить использование
Django ORM для выборки и обработки данных, проверить фильтрацию, сортировку,
пагинацию и агрегированную статистику, а также проанализировать SQL-запросы,
которые формирует ORM.

В отчёте приведены результаты для индивидуального проекта Moodboard creator.
В отличие от примера Roomly, предметная область проекта включает дизайнеров,
мудборды, каталоги и заказчиков и не содержит помещений или бронирований.

## 2. Выполненные задания Яндекс Практикума

В рамках текущего этапа выполнены задания, относящиеся к следующим темам:

- регистрация моделей в административной панели Django;

  `Coalesce`;
- проверка работы проекта, тестов и Git-контрольной точки.

## 3. Настройки административной панели Moodboard creator

Административная панель подключена по адресу `/admin/`. В проекте сохранены
стандартные приложения `django.contrib.admin`, `django.contrib.auth`,
`django.contrib.contenttypes`, `django.contrib.sessions`,
`django.contrib.messages` и `django.contrib.staticfiles`.

В Django Admin зарегистрированы модели:

- `Designer`;
- `Client`;
- `MoodboardCatalog`;
- `Moodboard`.

Для `DesignerAdmin` настроены отображение имени, пользователя и описания,
поиск по имени дизайнера, имени пользователя и электронной почте, сортировка
и inline-список мудбордов.

Для `ClientAdmin` настроены имя, электронная почта, компания, поиск по этим
полям и количество связанных мудбордов. Для `MoodboardCatalogAdmin` настроены
название, дизайнер, количество мудбордов, поиск и фильтрация по дизайнеру.

Для `MoodboardAdmin` настроены столбцы названия, дизайнера, каталога,
заказчика, цвета фона и даты обновления. Доступны поиск по собственным и
связанным полям, фильтрация по дизайнеру, каталогу и цвету фона, сортировка
по дате обновления, иерархия дат и 20 записей на страницу.

Связанные мудборды доступны inline в карточках дизайнера, заказчика и
каталога. Поля `created_at` и `updated_at` в карточке мудборда доступны
только для чтения.

## 4. Изменения моделей, миграций и QuerySet-менеджера

Структура моделей предметной области сохранена:

- `Designer` связан со стандартным пользователем через `OneToOneField`;
- `MoodboardCatalog` связан с дизайнером через `ForeignKey`;
- `Moodboard` связан с дизайнером, каталогом и заказчиком через
  `ForeignKey`;
- для каталога действует уникальность имени в пределах дизайнера.

В модель `Moodboard` добавлен пользовательский QuerySet-менеджер
`MoodboardQuerySet` со следующими методами:

- `with_related()` — добавляет `select_related` для дизайнера, каталога и
  заказчика;
- `search(query)` — фильтрует мудборды по названию;
- `for_designer(designer)` — ограничивает выборку мудбордами конкретного
  дизайнера.

Изменение менеджера не меняет структуру таблиц, поэтому новая миграция для
него не требуется. Проверка `python manage.py makemigrations --check`
завершилась сообщением `No changes detected`. Все существующие миграции
применены.

## 5. Проверенные ORM-запросы, фильтрация, сортировка, пагинация и статистика

Проверены следующие операции:

- получение списка через `Moodboard.objects.with_related()`;
- фильтрация через `Moodboard.objects.search("Пагинация")`;
- выборка объектов конкретного дизайнера через
  `Moodboard.objects.for_designer(designer)`;
- сортировка списка по `title` и стандартная сортировка по `updated_at`;
- получение конкретного мудборда через `get_object_or_404`;
- загрузка связанных дизайнера, каталога и заказчика через `select_related`;
- пагинация по 6 мудбордов на страницу с помощью `Paginator`;
- подсчёт количества мудбордов, дизайнеров и заказчиков через `aggregate`;
- группировка мудбордов по каталогам через `values` и `annotate`;
- подстановка названия «Без каталога» через `Coalesce`;
- подсчёт связанных мудбордов в административных списках через `Count`.

Переход между страницами списка сохраняет корректный QuerySet и не требует
предварительной загрузки всех объектов в список Python.

## 6. Проверка доступности помещений с учётом статусов бронирований

Этот пункт чек-листа Roomly неприменим к проекту Moodboard creator: в моделях
проекта отсутствуют `Room`, `Booking`, даты бронирования и статусы
`ACTIVE`, `CANCELLED`, `COMPLETED`. Поэтому проверка доступности помещений
не выполнялась и не имитировалась искусственными данными.

Для фактической предметной области проверены эквивалентные ограничения
связей: каталог можно выбрать только у текущего дизайнера, чужой каталог
отклоняется методом `assign_catalog`, а списки мудбордов фильтруются по
владельцу через `for_designer`.

## 7. Анализ SQL-запросов с помощью Django Debug Toolbar

Django Debug Toolbar подключена только для режима разработки:

- пакет добавлен в `requirements.txt`;
- приложение добавлено в `INSTALLED_APPS`;
- подключён `DebugToolbarMiddleware`;
- задан `INTERNAL_IPS = ["127.0.0.1"]`;
- маршрут `/__debug__/` подключается только при `DEBUG = True`.

Для страницы `/moodboards/` дополнительно выполнена проверка через
`CaptureQueriesContext`. При ответе со статусом `200` зафиксировано два
основных запроса:

1. `COUNT(*)` для определения количества страниц пагинации;
2. основной `SELECT` из `moodboards_moodboard` со связанным дизайнером,
   каталогом и заказчиком благодаря `select_related`.

Повторных запросов для обращения к этим связанным объектам не возникло.
Панель предназначена только для локальной разработки и не должна включаться
в производственном окружении.
